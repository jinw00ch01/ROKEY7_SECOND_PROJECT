# 2026-05-10 v2 사이클 종료 흐름 수정

직전 커밋 `0ec9465 feat(web_stt_firebase_v2): per-state terrain reactions + browser TTS fallback` 이후, 사용자 피드백으로 드러난 사이클 종료 흐름의 세 가지 결함을 수정한 작업 기록.

## 1. 배경 (Why)

음성 → 추천 → dispatch → 로봇 동작까지 전체 흐름은 동작했지만, UI 측면에서 다음 문제가 보였다:

1. **로봇이 명령을 *받기만* 해도 곧바로 "완료" 상태로 넘어감.** dispatching 단계가 깜빡이고 사라지니 terrain도 멈춘 것처럼 보였다.
2. **PROGRESS_STEPS의 라벨**이 "로봇 준비" — 실제로는 로봇이 동작하는 단계라 의미가 어긋났다.
3. **사이클 종료 후 idle로 안 돌아감.** 한 번 완료/에러 상태가 되면 새로고침해도 그대로 보였다. 다음 사이클 시작도 어색.
4. **에러가 발생하면 phase가 `"error"` 로 묶여** 사용자가 명시적으로 새로고침하지 않으면 "Voice: error" 표시가 사라지지 않았다.

원인은 모두 orchestrator의 사이클 종료 처리에 있었다.

## 2. 변경 파일 요약

| 파일 | 변경 |
|---|---|
| `web_stt_firebase_v2/src/lib/voice/session.ts` | `waitForRobotCompletion()` 신규, `publishDispatching()`에 `robot_state: ""` reset 추가 |
| `web_stt_firebase_v2/src/lib/voice/orchestrator.ts` | dispatch 후 task_done 대기, 사이클 종료 5초 후 자동 idle reset, error catch에서 throw 제거 |
| `web_stt_firebase_v2/src/App.tsx` | PROGRESS_STEPS dispatching 라벨 "로봇 준비" → "로봇 동작 중" |

## 3. dispatch ack vs 실제 task 완료

### 문제

`/task/start` (`std_srvs/srv/Trigger`)는 task_manager가 worker thread에 일감을 던지고 **즉시** `success=True` 로 응답한다 — 단순 ack에 불과하고 실제 픽이 끝났다는 신호가 아니다. 기존 흐름:

```ts
await publishDispatching(order);
await config.onDispatch(order);   // ← /task/start ack 받자마자 다음 줄로
await publishCompleted(order);    // 로봇이 아직 picking 중인데 completed로 표시
```

이 때문에 dispatching 표시가 0.x초만 보였다 사라지고 곧장 completed로 넘어갔다. UI에서는 "로봇이 한 번도 동작 안 한 것처럼" 보임.

### 해결: firebase_status_bridge가 쓰는 robot_state 구독

`cobot_voice/firebase_status_bridge.py`가 `/task/status`, `/task/result`, `/conveyor/place_ready`를 구독해서 `robot_session/current.robot_state` 필드를 다음 값으로 미러링한다:

- `detecting`, `picking`, `placing`, `task_done`, `error`

orchestrator는 dispatch 후 이 필드를 onSnapshot으로 구독해 `task_done` 또는 `error` 가 올 때까지 대기.

```ts
// session.ts
export function waitForRobotCompletion(timeoutMs = 180_000) {
  return new Promise<"done" | "error" | "timeout">((resolve) => {
    const unsub = onSnapshot(sessionRef(), (snap) => {
      const robotState = snap.data()?.robot_state;
      if (robotState === "task_done") finish("done");
      else if (robotState === "error")  finish("error");
    });
    const timer = setTimeout(() => finish("timeout"), timeoutMs);
    // ...
  });
}
```

```ts
// orchestrator.ts
if (config.onDispatch) {
  await publishDispatching(order);
  await config.onDispatch(order);
  const completion = await waitForRobotCompletion();
  if      (completion === "done")   await publishCompleted(order);
  else if (completion === "error")  await publishError("로봇 동작 중 오류가 발생했습니다.");
  else                              await publishError("로봇 동작 응답이 시간 내에 오지 않았습니다.");
}
```

### Stale state 방지: dispatch 직전 robot_state 클리어

이전 사이클의 `task_done` 이 doc에 남아 있으면 새 사이클 dispatch 직후 곧바로 false-positive로 잡혀 다시 즉시 completed가 되는 문제가 있다. `publishDispatching()` 에 `robot_state: ""` 도 같이 써서 reset.

`firebase_status_bridge`가 task_manager 진행에 따라 곧바로 `picking`/`placing` 으로 덮어쓰므로 빈 문자열이 보이는 시간은 사실상 한 tick 미만.

### timeout 180초

cluster push + verification round + 다중 너트 픽까지 고려한 보수적 cap. 부족하면 상수 한 줄만 조정하면 된다 (단, 실제로 timeout 도달했다는 건 진짜로 뭔가 끊긴 것일 가능성 높음).

## 4. 사이클 종료 후 자동 idle

### 의도

- 결과 화면(완료 메시지 / 에러)을 잠깐 사용자가 읽도록 5초 유지
- 그 후 자동으로 `resetSession()` 호출 → display_state="idle" + 모든 필드 비움
- 새로고침해도 stale 상태가 남지 않음
- stop 버튼 누르면 5초 sleep 즉시 끊고 곧장 reset

### 구현

```ts
// orchestrator.ts
const RESULT_DISPLAY_MS = 5000;

let idleResetTimer: ReturnType<typeof setTimeout> | null = null;
const cancellableSleep = (ms: number) =>
  new Promise<void>((resolve) => {
    idleResetTimer = setTimeout(() => { idleResetTimer = null; resolve(); }, ms);
  });

// ... main 흐름의 finally:
} finally {
  releaseStream();
  if (activeWake) activeWake.cancel();
  if (!cancelled) await cancellableSleep(RESULT_DISPLAY_MS);
  try { await resetSession(); } catch (e) { console.warn("resetSession failed:", e); }
}

return {
  result,
  cancel: () => {
    cancelled = true;
    if (idleResetTimer) { clearTimeout(idleResetTimer); idleResetTimer = null; }
    if (activeWake) activeWake.cancel();
    releaseStream();
  },
};
```

`cancellableSleep` 의 timer handle을 cancel handle에서 clearTimeout 하므로 stop 버튼 즉시 반응.

## 5. Error 시에도 idle phase로 흘러가기

### 문제

기존 catch 블록은 publishError 후 `throw error` 로 다시 던졌다. 그러면 result Promise가 reject되고 `useVoiceOrchestrator` 의 try/catch에서:

```ts
} catch (error) {
  setErrorMessage(error.message);
  setPhase("error");           // ← phase가 idle이 아니라 error로 잡힘
}
```

UI에 "Voice: error" 표시가 사라지지 않고, 다음 사이클 트리거하기 전까지 사용자에게 어색하게 남았다.

### 해결

orchestrator는 이미 `publishError(message)` 로 Firestore에 `display_state="error"` 를 쓰고, finally가 5초 후 `resetSession()` 으로 idle화한다. 그러면 useRobotSession 가 error 메시지/상태를 자동으로 보여주고 5초 뒤 비운다 — UI 측 phase까지 error로 묶을 이유가 없다.

```ts
} catch (error) {
  if (error instanceof CancelledError) {
    await updateDisplayState("idle");
    return null;
  }
  const message = error instanceof Error ? error.message : String(error);
  console.warn("Voice flow failed:", message);
  await publishError(message);
  return null;          // throw error 제거
}
```

이러면:
- result Promise는 정상 resolve → hook의 try가 통과 → `setPhase("idle")`
- 에러 메시지는 `robot_session.error` 필드에 5초 동안 보임 (App.tsx의 `{robotSession.error ? ... : null}` 블록)
- 5초 후 `resetSession()` 으로 error 필드도 비워짐 → UI에서 자연스럽게 사라짐

## 6. PROGRESS_STEPS 라벨 변경

```diff
- { label: "로봇 준비", states: ["dispatching"] },
+ { label: "로봇 동작 중", states: ["dispatching"] },
```

dispatching 단계는 이제 task_done까지 기다리는 *실제 동작 중* 시간이라 의미가 정합. headline (`DISPLAY_COPY.dispatching.headline = "로봇 동작 중"`) 과도 일치.

## 7. 사이클 한 번의 새 시각 흐름

```
idle (terrain 0.65/0.75)
 → wake_detected (1.05/1.1)
 → asking_state (speaking 1.25/1.5)            ← TTS
 → listening_state (listening 1.45/1.85)       ← 5s 녹음
 → transcribing_state (transcribing 1.95/2.7)  ← Whisper
 → asking_intensity (speaking)
 → listening_intensity (listening)
 → transcribing_intensity (transcribing)
 → recommending (processing 2.0/3.45)
 → result_ready (processing)
 → dispatching (processing) — robot_state=task_done까지 ★ 유지
 → completed (1.15/1.35) — 5초
 → idle (자동 reset) ★
```

★ 표시가 이번 패치의 새 동작.

## 8. 알려진 한계

- `RESULT_DISPLAY_MS = 5000` 이 너무 짧거나 길면 상수 조정 필요. 사용자 피드백 받으면서 조정.
- `waitForRobotCompletion` timeout 180초는 대부분의 cluster + verification 사이클에 충분하지만, 더 큰 주문이나 회수 단계가 길어지면 타임아웃 위험. 실제 도달 시 진짜 끊긴 것이라 가정하고 에러로 마감.
- error 처리에서 throw를 제거했으므로 외부에서 result Promise를 await 하는 호출자는 더 이상 에러를 catch할 수 없다 — 현재 호출자는 `useVoiceOrchestrator` 하나뿐이고 이미 의도한 동작이라 OK.
