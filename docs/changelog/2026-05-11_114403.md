# 2026-05-11 Firebase 데이터베이스 구조 조사 기록

`cobot2` 프로젝트가 Firebase에 어떤 구조로 데이터를 저장하는지 코드베이스 전수 조사한 결과. 향후 스키마 변경/마이그레이션 시 참고용.

## 1. 개요

- **DB 종류**: Firestore (Cloud Firestore). Realtime Database 아님.
- **프로젝트 ID**: `rokey-cobot2`
- **Auth Domain**: `rokey-cobot2.firebaseapp.com`
- **서비스 계정 키**: `src/secrets_4_firebase_config/rokey-cobot2-firebase-adminsdk-fbsvc-230a55fd91.json`
- **컬렉션 구조**: 단일 문서 패턴 — 모든 상태를 `/robot_session/current` 하나의 문서에 저장하고 모든 클라이언트가 `onSnapshot`으로 구독.

## 2. 단일 문서 경로

```
/robot_session/current
```

컬렉션 안에 여러 문서를 두지 않고 고정 ID `current` 하나만 사용한다. 이유:

- 로봇이 한 번에 한 사이클만 처리 → 동시 세션 개념 없음
- 모든 UI/백엔드가 같은 문서를 구독해서 실시간 상태 미러링
- 히스토리 보존은 별도 요구사항이 아니므로 매 사이클마다 같은 문서에 덮어쓰기 (`merge: true`)

## 3. 필드 스키마

### 3.1 음성 플로우 필드 (웹 UI ↔ Python 음성 모듈)

| 필드 | 타입 | 값 / 설명 |
|---|---|---|
| `display_state` | string | `idle`, `wake_detected`, `asking_job`, `listening_job`, `transcribing_job`, `asking_satiety`, `listening_satiety`, `transcribing_satiety`, `recommending`, `result_ready`, `dispatching`, `completed`, `error` |
| `question` | string | 현재 사용자에게 보여주는 질문 텍스트 |
| `transcript` | string | STT 인식된 사용자 발화 |
| `request_id` | string | 세션 ID (`YYYYMMDD_HHMMSS` 포맷) — 주문 중복 제거에 사용 |
| `categories` | array<string> | 추천 카테고리. v2 모델: `almond`/`cashew`/`pistachio`/`walnut` |
| `intensity` | string | 포만감 레벨: `low`/`normal`/`high` |
| `combo` | array<{nut, count}> | 구체 견과 + 개수 |
| `combo_text` | string | 사람이 읽을 수 있는 콤보 설명 |
| `confirm_message` | string | 최종 확인 메시지 |
| `success` | boolean | 추천 성공 여부 — `FirestoreOrderProvider` 가 dispatch 판단에 사용 |
| `error` | string | 오류 메시지 (App.tsx 에러 배너가 이 필드 구독) |
| `updated_at` | Timestamp | Firestore `serverTimestamp()` |

### 3.2 테마 필드 (`theme` 객체)

| 필드 | 값 |
|---|---|
| `theme.primary_category` | `""`/`fatigue`/`blood_sugar`/`diet`/`focus` |
| `theme.primary_nut` | `""`/`almond`/`cashew`/`pistachio`/`walnut` |
| `theme.primary_color` | hex (예: `#F2C879`) |
| `theme.secondary_color` | hex |
| `theme.accent_color` | hex |

카테고리 → 견과 → 색상 매핑:

```
fatigue      → cashew     (Gold:  #F2C879 / #FFF3D6 / #D99A36)
blood_sugar  → almond     (Brown: #B9855A / #F3E1D0 / #7A4E2D)
diet         → pistachio  (Green: #8BC34A / #E8F5D2 / #4F8A10)
focus        → walnut     (Dark:  #6D4C41 / #D7CCC8 / #3E2723)
```

기본 테마(`idle`): `#031B2D` / `#0B3552` / `#30C7F2`
에러 테마: `#3A1010` / `#F5C7C7` / `#E54848`

### 3.3 로봇 동작 필드 (로봇 백엔드 → UI)

| 필드 | 값 |
|---|---|
| `robot_state` | `detecting` → `picking` → `placing` → `conveyor_moving` → `task_done` (또는 임의 단계에서 `error`) |
| `robot_target_class` | 현재 집고 있는 견과 종류 |
| `robot_error` | 예: `home_failed`, `grasp_failed` |
| `robot_last_result` | 예: `success counts={'walnut': 1}` |

`display_state` 와 `robot_state` 를 분리한 이유: 음성 UI 플로우와 로봇 동작 진행을 독립적으로 관찰/구독하기 위해. dispatch 후 orchestrator는 `robot_state` 만 구독해서 `task_done` 대기 (직전 changelog `2026-05-10_161649.md` §3 참조).

## 5. 설계 특징

1. **단일 문서 + onSnapshot 패턴** — 별도 pub/sub 인프라 없이 모든 클라이언트가 동일 상태를 실시간 공유
2. **`merge: true` 부분 업데이트** — 모든 쓰기가 partial update라 필드끼리 덮어쓰지 않음
3. **Python 비동기 큐** — Firebase 응답 지연이 음성 파이프라인 블로킹하지 않도록 워커 스레드 + 큐
4. **Graceful degradation** — `_FIREBASE_UNAVAILABLE` 플래그로 Firebase 끊겨도 로봇 동작은 계속
5. **`request_id` 중복 제거** — 같은 주문이 세션 재시작 시 재실행되지 않도록 ID 추적
6. **display_state vs robot_state 분리** — UI 플로우와 로봇 진행이 다른 주기로 진행되므로 분리 필드
7. **dispatch 직전 `robot_state: ""` 리셋** — 이전 사이클의 `task_done` 잔여가 false-positive로 잡히는 것 방지 (직전 changelog §3 참조)

## 6. 주의 사항

- **보안 규칙이 열려 있음** — `firestore.rules` 현재 인증 없이 read/write 허용. 외부 배포 전 Firebase Auth 필수.
- **단일 문서 = 동시 세션 불가** — 여러 사용자가 동시에 주문하는 시나리오는 현재 구조에서 지원 안 됨. 필요 시 컬렉션화 + 활성 세션 인덱스 추가 필요.
- **히스토리 없음** — 매 사이클마다 덮어쓰므로 과거 주문 기록을 보려면 별도 컬렉션 (예: `robot_session_history/{request_id}`) 신설 필요.
- **서비스 계정 키 commit 위험** — `secrets_4_firebase_config/*.json` 은 `.gitignore` 확인 필수.

## 7. 후속 작업 후보 (메모)

- 사용자 발화/주문 히스토리 별도 컬렉션 분리
- Firestore 보안 규칙 — 익명 인증 또는 디바이스 토큰 기반
- 동시 세션 지원이 필요해질 경우 단일 문서 → `robot_session/{session_id}` + 활성 세션 포인터 패턴으로 마이그레이션
